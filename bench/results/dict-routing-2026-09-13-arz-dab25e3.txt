# Plan items 61 and 43: is the block search where the lookup's time is, and does a cache-line-wide
# node beat the binary search over the samples?
# lexindex 2.1.0 at dab25e3 in a worktree (`/tmp/lexindex-stree`, `local/stree`), arz (Ryzen 7
# 5800HS, Zen 3), rustc 1.98.1, 2026-09-13, machine otherwise idle (load average under 1).
#
# One process, one index, one probe list. `SEARCH_MODE` selects the sample search *inside*
# `locate`, so the lanes differ in nothing else, and every lane is checked to answer what the
# shipped search answers on every probe before any of them is timed. Lanes run as a palindrome
# (0, 1, 2, 3, 3, 2, 1, 0) so a drift that is linear over a round cancels, and a `StringIndex`
# lane no lane can touch runs alongside as the control.
#
#   binary  the shipped pair of `partition_point`s over `samples`
#   tree    levels of eight `u64`, each entry the maximum of its group below, derived at load
#           (nb/7 words, 44 KB at ten million); both bounds in one descent, scalar nodes
#   scan    one `partition_point` and a walk over the run of equal samples -- no second structure
#   avx2    the tree with `_mm256_cmpgt_epi64` nodes, rank by bit scan rather than `count_ones`
#           (`popcnt` is not in the baseline target and AVX2 does not imply it)
#
# Three lanes price the lookup itself, all on the same code `locate` runs:
#
#   search  `sample_of` and both bounds                     (`probe_sample_range`)
#   block   the same plus the head boundary                 (`probe_block`)
#   rest    the scan once the block is known                (`probe_locate_in`)
#
# `id` is not `block + rest`: at ten million the two halves take cache from each other and the
# residual is ~50 ns of 615. At half a million there is nothing to compete for and they add to
# within 0.5 %.

## What it says

# Where the time is, quiet machine, members only, block 256:
#
#   corpus            id      search   head boundary   scan, block known   routing / id
#   words 480 k    273.4     22.4          22.7              229.2            16 %
#   titles 10 M    614.9     37.1          48.0              477.7            14 %
#   titles 10 M    738.7     40.6          79.5              622.2            16 %   (20 k probes)
#
# The routing is a sixth of a lookup and the block scan is the rest. The 2026-09-12 file put the
# block search at 31 % of 835 ns at ten million (152 the samples, 107 the head boundary); that run
# was an instrumented worktree and its `id` baseline is 20-35 % above this one's. Neither the share
# nor the absolute survives a quiet, uninstrumented, in-process measurement.
#
# The wide node loses, and not by a little. Five levels of eight beat fifteen binary steps on
# *accesses* and lose on *work*: a node is eight compares and a rank where a binary step is one
# compare and a conditional move, the descent is strictly serial where the two `partition_point`s
# are independent chains the out-of-order engine overlaps, and the first eight steps of a binary
# search re-read the same 255 elements for every probe -- 2 KB, permanently in L1. AVX2 nodes take
# the tree from 53 to 43 ns (-19 %) and it is still 16 % above the binary search.
#
# End to end the tree is worth nothing: +0.1 % on `id` at ten million with members only, -1.3 to
# -2.8 % with half the probes misses, +4.4 % on the dictionary. Below the 5 % bar in every cell,
# and negative at half a million keys. 61 and 43 close.
#
# The one lane that beats the shipped search -- one `partition_point` and a walk over the run of
# equal samples -- is worth -30 % of the search at 480 k and -9 % at ten million, which is 7 ns of
# 273 and 3.4 of 615. `id` does not move on it. Not shipped.
