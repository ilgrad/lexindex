bench/frontier/frontier_lex at 152a00f (the in-memory build's passes over the keys rewritten): how
long `DictIndex::build_with_block` takes over the thirteen corpora of the million-key frontier, at
blocks 1024 and 256, in three versions of the library --

  v4.2.0    the tag; before the character code
  v4.3.1    the tag; the character code, whose in-memory build counted the keys' bytes outside
            ASCII, their characters and their spelling in three passes on one thread
  152a00f   the tree under test

Each version is its own build of the harness from that tree, built as bench/frontier builds it
(release, thin LTO, one codegen unit, no target-cpu). One process a corpus and version: it reads the
corpus a line at a time, sorts and deduplicates the keys itself -- so every build is handed keys in
order, whose bytes lie in the heap in the file's order -- and builds block 1024, then block 256,
timing each build on its own. The lookups the harness then runs are not what this file is for. Six
rounds; within a round each corpus in turn, and for each the three versions in the order above in
odd rounds and in the reverse order in even ones. Each cell is the median of six builds in ms and,
in brackets, the fastest and slowest. The blobs 152a00f writes are the size 4.3.1's are on all 26
cells, and the crate's golden files hold them byte for byte.

AMD Ryzen 7 5800HS (8 cores, 16 threads, 16 MB L3), 38 GiB DDR4-3200 in unequal channels (layout
not read here -- needs root), Fedora 44, Linux 7.2.7-200.fc44.x86_64, rustc 1.98.1, governor
