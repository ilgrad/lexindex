n distinct splitmix64 keys; one process per (n, thread count), rows built A-B-A-B for 3 rounds (builds: min),
lookups over one shuffled probe order of all n keys (min of 9 passes). The probe keys are copied into an array
in probe order, so the lookup column is the function alone; each row's lookup loop is a generic function of its
own (`sweep`), so that the function is inlined into a loop and nothing else.
spread = slowest repeat over the fastest, minus one; batch = lexindex `Mphf::index_all` / ptr_hash
`index_stream::<32, _>` over chunks of 4096 keys (ph has no batch form).
build peak MB = the process's peak resident size over the build (`VmHWM` after a `clear_refs` reset) above its
resident size before it: the construction memory beyond the keys and the probe order, exact for the tables that
are mmap'd whole (10 M and 100 M); below that the allocator's reuse of freed heap hides part of it (fast at 1 M).
huge MB = `AnonHugePages` from `/proc/self/smaps_rollup` right after the build: the 2 MiB pages backing the table.
Only lexindex's tables ask for them (`MADV_HUGEPAGE` from 2 MiB up); the control lane runs the same process under
`prctl(PR_SET_THP_DISABLE)`.
lexindex takes the keys as hashes; ph hashes each key with wyhash at build and on every lookup level; ptr_hash
hashes with FastIntHash (one multiply).
