local/idfast at af19cb7 (a coded blob routes the query's own UTF-8, and no lookup reads a head the
samples settle): what `DictIndex::id` and `ids_of` cost at the default block in three builds of the
library over the same keys, in one process --

  4.2.0     from crates.io; every blob `BDX3`
  4.3.2     the tag v4.3.2; `BDX4` where the character code pays
  af19cb7   the tree under test, which has to write 4.3.2's blob byte for byte -- the harness
            asserts that on every corpus

Fourteen of the files `bench/corpora.json` names: the thirteen corpora of the million-key frontier
and jieba's lexicon (349 045 keys). Three of them take the character code: jieba's lexicon and the
million Chinese and Russian titles. Per corpus, 200 000 probes, every one a hit, shuffled with a
fixed seed and laid end to end in one arena so that the probes' own bytes stream. Before any timing,
the ids every build's `id` and `ids_of` give over the probes are checked to sum alike, and the
first 20 000 probes' ids to agree one by one. Each build's index is loaded from its blob twice, so that one placement
in physical memory is not mistaken for the code; within a load, an untimed pass of every op, then
five rounds of the seven ops -- a `HashMap<&str, u64>` lookup of the same probes as the control,
which no build can move, then `id` in each build, then `ids_of` in each -- in that order and then in
the reverse one, every timed pass right after an untimed pass of the same op. 20 timed passes an op;
each line gives the median and, in brackets, the minimum, in ns a probe. `id` takes a `&str` and is
called in a loop; `ids_of` takes the 200 000 probes as one slice.

The whole run was taken twice, by two builds of the harness whose code layout differs -- the second
has its functions in the reverse order behind a padding function -- since on a probe loop like this
alignment alone moves a few per cent. Both are below. Built release, thin LTO, one codegen unit.

AMD Ryzen 7 5800HS (8 cores, 16 MB L3), 38 GiB DDR4-3200 in unequal channels (layout not read here
-- needs root; the physical placement of each load not recorded), Fedora 44, Linux
7.2.7-200.fc44.x86_64, rustc 1.98.1, governor powersave. The run started only once a readiness
check passed -- one-minute load 0.36, no swap in use, no other process over 15 % CPU, 5.3 h up
after a reboot -- and the hottest thermal zone read under 70 C: 50 C at the start of each build's
run, which the second waited for, and 93 C at the end of each. The one-minute load at the end, 1.03,
is the run's own.

How far to trust a line: across the two builds, 4.2.0's own `id` lines agree within 2.3 % on
thirteen corpora of the fourteen, and its `ids_of` lines within 4.7 %. The fourteenth is idents in
the first build, where every line of the row, the control's included, reads 9-25 % above the second
build's -- something outside the code, and that row's ratios are out of line with the second
build's. The control's median moves by up to 32 % between the two processes on the four smallest
corpora (jieba, words, numeric, pypi), where a `HashMap` lookup is fastest and each process builds
its own table, and within 3.3 % on the other nine. So a difference of two or three per cent between
builds of the library means something only inside one run, where they alternate, and only where
both harness builds agree on it.
