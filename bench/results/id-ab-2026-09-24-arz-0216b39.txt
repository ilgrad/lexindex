The tree under test has to write 4.3.3's blob byte for byte at every block -- the harness asserts
that on every corpus. The thirteen corpora of the million-key frontier, then the six of ten million.
Per corpus, 200 000 probes, every one a hit, shuffled with a fixed seed and laid end to end in one
arena so that the probes' own bytes stream. Before any timing, the ids every op gives over the
probes are checked to sum alike, and the first 20 000 probes' ids to agree one by one at every
block. Each index is loaded from its blob twice, so that one placement in physical memory is not
mistaken for the code; within a load, an untimed pass of every op, then five rounds of the thirteen
ops -- a `HashMap<&str, u64>` lookup of the same probes as the control, which no build can move,
then `id` at each block in 4.3.3, u and r, then `ids_of` in each -- in that order and then in the
reverse one, every timed pass right after an untimed pass of the same op. 20 timed passes an op;
each line gives the median and, in brackets, the minimum, in ns a probe, then the change against
4.3.3, and for r in parentheses the change against u. `id` takes a `&str` and is called in a loop;
`ids_of` takes the 200 000 probes as one slice. u and r run the same machine code: a lookup reads
whether the words are there.

The whole run was taken twice, by two builds of the harness whose code layout differs -- the second
has its functions in the reverse order behind a padding function -- since on a probe loop like this
alignment alone moves a few per cent. Both are below. Built release, thin LTO, one codegen unit.

AMD Ryzen 7 5800HS (8 cores, 16 MB L3), 38 GiB DDR4-3200 in unequal channels (layout not read here
-- needs root; the physical placement of each load not recorded), Fedora 44, Linux
7.2.7-200.fc44.x86_64, rustc 1.98.1, governor powersave. Each of the four runs started only once a
readiness check passed -- one-minute load 0.30-0.38, no swap in use, no other process over 15 % CPU,
2.2-2.7 h up after a reboot -- and the hottest thermal zone read under 70 C: 47-50 C at the start of
every run, 93 C at the end of each million-key run and 85-87 C at the end of each ten-million one.
The one-minute load at the end, 1.00, is the run's own.

How far to trust a line: across the two builds, 4.3.3's own lines agree within 2.7 % at a million
keys (median 1.1 %) and within 5.2 % at ten million (median 0.5 %), the widest `opaque` at block
256. The control agrees within 6.5 % at a million keys -- widest on `words` and `numeric`, where a
`HashMap` lookup is fastest and each process builds its own table -- and within 0.7 % at ten million.
The routed lines agree within 5.3 % at a million keys and 9.8 % at ten million, both on `opaque`. So
a difference of a few per cent means something only inside one run, where the indexes alternate,
and only where both harness builds agree on it.
